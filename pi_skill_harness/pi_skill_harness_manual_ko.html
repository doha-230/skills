01 · 개념

이 프로그램은 무엇을 하나요?

같은 작업을 여러 번 시켜 보고, 품질을 유지하면서 더 빨리 끝내는 SKILL.md를 찾는 프로그램입니다. Python이 실험을 관리하고, Pi가 실제 업무를 수행하며, 로컬 LLM이 지침 수정안을 제안합니다.

01

사용자가 정의

대상 스킬, 대표 작업, 입력 파일, 완료 조건과 품질 기준을 정합니다.

02

하네스가 반복

원본과 후보를 새 세션·새 작업폴더에서 교차 실행하고 결과와 시간을 기록합니다.

03

검증 후 선택

별도 작업으로 최종 검증합니다. 수동 평가 작업은 사용자가 검토한 뒤 승인합니다.

가능한 일현재 구현의 범위
코드·보고서·PPT·Excel·그래프 스킬 비교작업 유형을 엔진이 가정하지 않습니다. TASKS와 검증기를 바꿉니다.
SKILL.md 자동 개선본문만 수정합니다. YAML 앞부분과 보조 파일은 유지합니다.
반복 실행·시간 측정·원본 대비 비교실패한 실행을 제외해 속도만 좋게 보이도록 계산하지 않습니다.
품질 검증파일·텍스트·JSON·외부 명령 + 수동 또는 텍스트 AI 평가
자동으로 해주지 않는 일실무 테스트 설계, 모든 파일의 의미 해석, 소프트웨어 설치, 원본 스킬 배포
범용이라는 뜻

하네스 엔진을 바꾸지 않고 작업과 평가 기준을 바꿀 수 있다는 뜻입니다. 모든 작업의 정답을 자동으로 판단하는 것은 아닙니다.

02 · 처음 실행

처음에는 이 순서로 진행하세요

  1. 실행 환경을 준비합니다

    Python 3.10 이상, 정상 동작하는 Pi, 실행 중인 로컬 LLM 서버를 준비합니다. 하네스 자체는 표준 라이브러리만 쓰지만, 실제 업무에 필요한 라이브러리와 프로그램은 별도로 있어야 합니다.

  2. 작업 폴더를 나눕니다

    하네스, 스킬, 입력, 결과, 검증기를 구분합니다. 입력 폴더나 스킬 폴더 안에 결과 폴더를 만들지 마세요.

예시 경로내용
C:/PiHarness/pi_skill_harness.py실행 파일
C:/AgentSkills/report/SKILL.md개선 대상. 같은 폴더의 보조 파일도 함께 복사
C:/PiHarness/inputs/train/source.txt개선에 사용할 실제 입력
C:/PiHarness/inputs/holdout/source.txt마지막 검증에 사용할 다른 입력
C:/PiHarness/validators/선택 사항: 사용자가 작성한 검증 코드
C:/PiHarness/output/자동 생성되는 실험 결과

  1. 설정과 작업을 작성합니다

    다음 장의 settings.json 예시를 자신의 업무에 맞게 바꿉니다. 모델 이름과 경로는 실제 값으로 교체해야 합니다.

  2. 자체 검사 → 환경 확인 → 실행

    PowerShell에서 하네스가 있는 폴더로 이동한 후 실행합니다.

PowerShell
Set-Location C:\PiHarness
python pi_skill_harness.py selftest
python pi_skill_harness.py doctor --config settings.json
python pi_skill_harness.py run --config settings.json
각 명령의 차이

selftest는 Pi·LLM 없이 내부 검사 로직을 테스트합니다. doctor는 설정과 Pi 옵션을 확인하며 API 연결을 시험하지 않습니다. 실제 Pi·모델 연결은 run에서 확인합니다.

  1. 결과 검토 후 필요한 경우 승인합니다

    결과 폴더의 final_decision.json을 확인하고, 수동 보류 상태라면 review.html과 원본 파일을 열어 검토합니다. 승인 명령은 승인과 적용에서 설명합니다.

03 · 설정 파일

Python을 수정하거나 JSON으로 분리할 수 있습니다

방법 A: Python 파일 상단의 CONFIG, TASKS 등을 직접 수정합니다. 이 경우 --config 없이 실행합니다.

방법 B: 실행 코드와 업무 설정을 분리하려면 settings.json을 만들고 --config settings.json을 붙입니다. 아래는 문서 요약 스킬용 전체 설정 예시입니다. 경로, 모델, 입력 내용은 교체해야 합니다.

설정을 덮어쓰는 규칙

설명서를 열어 이 버튼으로 예시를 저장할 수 있습니다. YOUR_… 값과 파일 경로를 실제 환경에 맞게 수정한 뒤 사용하세요.

입력 파일은 별도로 준비하세요

inputs/train/source.txt에는 대표 업무 자료를, inputs/holdout/source.txt에는 다른 자료를 넣습니다. 두 입력을 동일하게 만들면 최종 검증의 의미가 약해집니다. 파일명은 같아도 내용은 달라야 합니다.

JSON 문법

Python은 True / False, JSON은 true / false를 사용합니다. JSON에는 주석과 마지막 쉼표를 넣지 마세요. Windows 경로는 C:/PiHarness/…처럼 슬래시를 쓰면 편합니다. 설정 JSON은 UTF-8 BOM 없이 저장하세요.

04 · 실행 환경

Pi 모델과 개선 모델 설정은 서로 다릅니다

같은 서버와 모델을 써도 Pi가 작업하는 연결과 하네스가 개선안을 요청하는 연결은 따로 설정해야 합니다.

구분관련 설정의미
업무 실행: Pipi_provider, pi_modelPi에 이미 등록되어 있는 provider와 모델 ID. 서버 URL은 Pi의 등록 설정에서 정합니다.
지침 개선: 하네스api_base, optimizer_modelOpenAI 호환 /chat/completions API를 직접 호출합니다.
텍스트 품질 평가: 하네스judge_model같은 api_base를 사용합니다. 기본값 CHANGE_ME이면 개선 모델을 재사용합니다.
인증·등록 파일pi_agent_template기본 ~/.pi/agent의 models.json과 auth.json만 실행별 임시 설정으로 복사합니다.
API 인증api_key_env하네스 API 키를 읽을 환경변수 이름. 기본 LOCAL_LLM_API_KEY, 값이 없으면 local 사용
Pi 환경변수pi_envPi 자식 프로세스에만 추가합니다. 외부 검증기는 이 추가 값을 자동으로 받지 않습니다.
api_base만 바꾸면 Pi도 연결되나요?

아닙니다. api_base는 개선·텍스트 평가용입니다. Pi는 pi_agent_template의 모델 등록과 pi_provider / pi_model을 사용합니다.

PowerShell
# 필요한 경우 하네스 API 키를 현재 PowerShell에 설정
$env:LOCAL_LLM_API_KEY = "실제키"

# Pi 설치 경로 확인
Get-Command pi -All
Get-Command node

Windows에서 pi.cmd를 찾지 못할 때

기본값은 ["pi.cmd"]입니다. 지원되는 npm 설치 경로에서는 내부적으로 Node와 cli.js로 변환합니다. 자동 해석에 실패하면 확인한 실제 경로를 지정하세요.

JSON 설정 일부
"pi_command": [
  "C:/Program Files/nodejs/node.exe",
  "C:/실제설치경로/node_modules/@earendil-works/pi-coding-agent/dist/cli.js"
]
실험 환경의 차이

기존 Pi의 settings.json 전체, 전역 스킬, 확장, 프롬프트 템플릿, AGENTS.md는 이 실행에 그대로 상속되지 않습니다. 지정 스킬은 명시적으로 로드합니다. 확장 도구에 의존하는 스킬은 현재 실행 방식에서 실패할 수 있으므로 별도 통합이 필요합니다.

05 · 작업 정의

TASKS에는 무엇을 적나요?

키필수/기본작성 방법
id필수작업 고유 이름. 영문·숫자·밑줄·하이픈만 사용
split필수train: 개선용 / holdout: 최종 검증용. 각각 최소 1개
prompt필수실제 작업 지시. 결과 파일명과 완료 조건을 명시
seed_dir입력 없으면 빈 문자열매 실행에 복사할 입력 폴더. 가급적 절대 경로 사용
artifacts필수, 비어 있으면 안 됨결과 파일의 상대 glob 목록. 각 패턴에 최소 한 파일 필요
checks필수, 비어 있으면 안 됨자동 필수 검사 목록
quality_mode필수manual / llm_text / checks_only 중 하나
quality_rules필수사람·AI가 확인할 품질 기준. Pi 작업 지시에도 전달
read_only_inputs기본 []변경 감지할 입력 glob. 지정하면 seed_dir와 해당 입력이 필요
allow_existing_artifacts기본 false입력에 이미 결과 파일이 있는 수정 작업이면 true
require_artifact_changes기존 결과 허용 시 기본 true각 결과 패턴에 새 파일 또는 변경된 파일이 최소 1개 있어야 함

결과 패턴 작성 예

예시의미
report.md현재 작업폴더의 정확한 파일명
output/*.pptxoutput 폴더 바로 아래 PPTX
src/**/*.pysrc 아래 재귀적으로 Python 파일 탐색
입력과 결과를 구분하세요

artifacts에 **/*를 넣으면 입력 파일까지 결과로 잡힐 수 있습니다. 구체적인 결과명이나 전용 output 폴더를 쓰세요. 절대 경로와 .. 패턴은 사용하지 않습니다.

train과 holdout의 차이

train은 후보를 고르는 과정에서 반복 사용합니다. holdout은 후보 탐색이 끝난 뒤 선택된 후보만 평가하는 별도 작업 집합입니다. “한 번 검증”은 실행 한 번이 아니라 최종 평가 단계 한 번을 뜻하며, 이 단계 안에서도 holdout_repeats만큼 반복합니다.

holdout 결과를 보고 지침을 계속 고치면 그 작업은 더 이상 독립 검증 자료가 아닙니다. 새 실험을 시작할 때도 같은 holdout에 맞춰 조정하지 않도록 별도 자료를 마련하세요.

06 · 필수 검사

평가 기준은 checks와 quality_rules에 나눠 씁니다

checks는 Python이 통과·실패를 판정할 조건입니다. quality_rules는 정성적 요구사항입니다. 예를 들어 “슬라이드 파일이 있다”는 자동 검사로, “핵심 주장이 명확하다”는 품질 기준으로 작성합니다.

검사 유형설정검사하는 내용
filespattern, min_count, max_count, min_bytes파일 개수와 최소 크기. 문서가 정상으로 열리는지까지 확인하지 않음
textpath, contains, regex, min_chars, encoding필수 문자열, 정규식, 최소 길이. 기본 UTF-8-SIG. 문자열 검사는 대소문자를 구분
jsonpath, equals, required_keysJSON 파싱 및 지정 값·최상위 키 존재 확인. 숫자 허용 오차 기능은 없음
commandargv, timeout사용자 검증 프로그램 실행. 종료 코드 0 통과, 그 외/시간 초과 실패
checks 형식 예시 · 네 결과물이 있는 작업에만 함께 적용
[
  {"type": "files", "pattern": "deck.pptx", "min_count": 1, "max_count": 1, "min_bytes": 1000},
  {"type": "text", "path": "report.md", "contains": ["결론"], "min_chars": 200},
  {"type": "json", "path": "metrics.json", "equals": {"summary.total": 15}, "required_keys": ["summary"]},
  {"type": "command", "argv": ["{python}", "C:/PiHarness/validators/check.py", "{work}"], "timeout": 60}
]

여러 검사는 모두 통과해야 합니다. JSON의 summary.total은 중첩 키이며 items.0.name처럼 목록 인덱스도 사용할 수 있습니다.

외부 검증기의 규칙

  • {python}은 CONFIG의 python_exe, {work}는 해당 실행의 작업폴더로 치환합니다.
  • 명령은 문자열 한 줄이 아닌 인수 배열입니다. 파이프·리다이렉션·셸 문법은 자동 해석하지 않습니다.
  • 검증 스크립트는 수정 대상 스킬과 입력 폴더 밖에 두고 절대 경로로 지정하세요.
  • 검증기는 결과물을 읽기만 해야 합니다. 검증 과정에서 결과물이 바뀌면 실패합니다.
  • 출력은 logs/check_0.stdout.log, 오류는 logs/check_0.stderr.log 등에 남습니다.
검사 통과의 의미

파일 존재·크기 검사는 최소 확인입니다. 수치 정확성, 수식, 슬라이드 수, 데이터 일치 같은 실무 조건은 전용 검증 코드나 수동 검토로 보완해야 합니다.

07 · 정성 평가

manual · llm_text · checks_only 중 선택

모드적합한 작업최종 처리
manualPPT·Word·Excel·이미지, 중요 보고서자동 검사와 시간 기준을 통과해도 수동 승인 전에는 원본 유지
llm_textMarkdown·텍스트·JSON·소스 코드 등A/B 순서를 바꿔 두 번 평가. 일관되게 동등 또는 후보 우수이면 통과
checks_only전용 검증기로 충분히 판정 가능한 작업자동 검사와 시간 기준만으로 채택. 검사 설계가 품질 범위를 결정

AI 평가가 보류되는 경우

바이너리 파일, 허용되지 않은 확장자, UTF-8로 읽지 못하는 파일, 텍스트 길이 초과, API 오류, 판단 불일치, uncertain은 수동 검토로 넘어갑니다. 두 번 모두 원본이 우수하다고 평가하면 품질 탈락입니다.

기본 judge_max_chars=20000은 한쪽 결과물 묶음의 문자 수 한도입니다. 긴 결과를 임의로 잘라 AI에게 보내지는 않습니다. 텍스트 AI는 PPTX·PDF·이미지를 직접 보지 않습니다. 예를 들어 HTML 소스를 읽어도 실제 화면 배치를 확인한 것은 아닙니다.

quality_rules 작성 예

“좋게 작성할 것” 대신 “원문의 모든 수치와 단위를 보존한다. 근거가 없는 결론은 쓰지 않는다. 독자가 실행할 조치를 구체적으로 제시한다”처럼 관찰할 수 있는 기준을 적으세요.

전역 프롬프트와 작업별 기준

위치역할
TASKS[i].checks해당 작업의 자동 필수 조건
TASKS[i].quality_rules해당 작업의 내용·형식·품질 기준
JUDGE_PROMPT모든 llm_text 작업에 공통 적용할 AI 평가 방식
OPTIMIZER_PROMPT스킬을 어떻게 수정할지에 대한 공통 지침
EVAL_CONFIG완료시간 개선을 채택할 숫자 기준
manual이어도 후보 생성은 자동입니다

수동 검토가 남아 있는 후보도 탐색 중에는 잠정 기준으로 선택되어 다음 개선에 쓰일 수 있습니다. 다만 최종 채택은 하지 않습니다. 마지막에는 최초 원본과 다시 비교합니다.

09 · 반복과 시간

몇 번 실행하고, 어떻게 빨라졌다고 판단하나요?

설정기본값의미
rounds1개선 후보를 생성할 횟수
repeats5train 작업별 원본/후보 쌍 수. 원본 5회 + 후보 5회
holdout_repeats5holdout 작업별 비교 쌍 수
warmuptrue최초 train 작업으로 1회 예열. 비교 지표에서는 제외
timeout_seconds600Pi 실행 1회 제한 시간. 실패하면 해당 비교는 통과하지 못함
min_improvement_percent10.0전체 작업 기준 최소 시간 개선율
max_task_regression_percent5.0개별 작업에서 허용할 최대 시간 악화율
require_positive_bootstrap_lower_boundtrue반복 재표본화 구간의 하한도 0%보다 커야 함
bootstrap_samples2000재표본화 횟수. Pi를 2000번 실행한다는 뜻이 아님

각 작업에서 후보 시간 / 원본 시간의 중앙값을 계산하고, 작업별 비율을 같은 가중치의 기하평균으로 합칩니다. 모든 실행이 필수 검사를 통과해야 하며, 최종 train 재검증과 holdout 모두 기준을 만족해야 합니다.

측정 시간은 Pi 프로세스 시작부터 종료까지입니다. 입력 복사와 외부 검증 시간, 후보 생성·AI 평가 시간은 이 지표에 포함하지 않습니다. 따라서 실제 전체 대기시간은 더 깁니다.

실행 횟수 계산기

32회Pi 실행만 약 32분

warmup=true 기준. 후보 생성과 필수 검사·AI 평가의 추가 시간은 제외한 상한 계획값입니다. 채택 후보가 없거나 중간 실패하면 실제 실행은 줄어듭니다. 이 계산기는 하네스 설정을 변경하지 않습니다.

실행 횟수 공식
최대 Pi 실행 수 = W + T + 2×T×R×N + 2×T×R + 2×H×Rh
W: 예열(0 또는 1), T: train 수, H: holdout 수
R: repeats, Rh: holdout_repeats, N: rounds
해석의 한계

기본 5쌍과 bootstrap은 탐색을 위한 기준이지 통계적 보증은 아닙니다. GPU 부하와 서버 상태를 일정하게 유지하세요. 새 Pi 세션이어도 LLM 서버의 캐시가 자동 초기화되지는 않습니다.

11 · 승인과 적용

승인은 결과 폴더의 best_SKILL.md만 바꿉니다

pending_manual_review인 후보의 최종 결과를 검토합니다. final과 regression의 reference는 최초 원본입니다. 후보의 사실 정확성, 기능 누락, 문서 배치 등을 고정 품질 기준에 따라 비교하세요.

PowerShell
python pi_skill_harness.py approve "C:/PiHarness/output/실제_실험폴더" --confirm-reviewed

통과하면 candidate_SKILL.md가 같은 결과 폴더의 best_SKILL.md로 복사되고 approval.json이 생깁니다. 검토 대상 파일이나 판정 파일이 바뀌면 해시 검사로 승인이 거부됩니다.

승인 후 상태 파일

현재 구현은 수동 승인 후에도 final_decision.json의 과거 판정을 덮어쓰지 않습니다. 승인 완료 여부는 approval.json의 approved_by_user와 best_SKILL.md를 함께 확인하세요.

실제 스킬에 적용할 때

  1. 현재 원본 SKILL.md를 백업하거나 Git으로 기록합니다.
  2. 검증한 best_SKILL.md와 원본의 차이를 확인합니다.
  3. 승인한 best_SKILL.md를 실제 스킬 폴더의 SKILL.md로 직접 적용합니다.
  4. 보조 파일은 원래 구성을 유지하고, 실제 사용 환경에서도 대표 작업을 확인합니다.

하네스는 원본을 자동으로 덮어쓰거나 Pi 환경에 배포하지 않습니다. 후보를 채택하지 않으려면 승인 명령을 실행하지 않으면 됩니다.

  • 기존 하네스 전체가 아니라 SKILL.md 본문을 개선합니다. 보조 프로그램 자체는 최적화하지 않습니다.
  • 실행별 새 Pi 프로세스와 설정을 만들고 작업폴더를 복사합니다. 서버 캐시 초기화나 OS 권한 격리는 하지 않습니다.
  • read_only_inputs는 변경 감지 조건이며 쓰기 권한을 차단하는 기능은 아닙니다.
  • Pi 작업에 필요한 프로그램·폰트·라이브러리·서버는 별도 준비해야 합니다. 폐쇄망 환경에서는 사전에 준비하세요.
  • 환경을 매번 복사하므로 입력 또는 스킬 폴더가 크면 디스크 사용량과 준비 시간이 늘어납니다.
  • 원본이 실패하는 작업을 자동으로 수리하는 목적이 아닙니다. 원본이 필수 조건을 통과한 뒤 더 빠른 후보를 찾습니다.
  • 도구별 지연 분석이나 토큰 통계는 내장되어 있지 않습니다. 현재 개선 피드백은 실행시간·검사 실패·판정 중심입니다.
